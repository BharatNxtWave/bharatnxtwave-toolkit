# BharatNXT Wave — Deploying to Render

Everything needed to run this app on Render, end to end.

---

## 0. Read this first

This app was built for an office LAN. Two things change on Render, and you
should decide they are acceptable before going further.

**The app gets a public URL.** `https://<name>.onrender.com` is reachable from
anywhere on the internet. What keeps strangers out is the office IP allow-list
(section 6) plus the login form. On the LAN deployment the network itself was
the first wall; here that wall is a header check. It works, but it is a
different level of assurance.

**Your data leaves the office.** Scheme sources, client collections and flyers
sit on Render's infrastructure. Render has no India region — the nearest is
**Singapore**. If BharatNXT has a data-residency rule, resolve it before
deploying, not after.

Neither of these is a blocker. They are simply things to say out loud.

### What you need before starting

| | |
|---|---|
| A **static public IP** at the office | Without it the allow-list has nothing stable to allow. If the office IP changes, everyone is locked out until you update it. |
| A paid Render plan | The persistent disk in section 3 requires it. Free instances have no disk, and your uploaded flyers would be deleted on every deploy. |
| The repository on GitHub/GitLab | Render deploys from a connected repo. |

## 1. What Render actually runs

Render builds the [`Dockerfile`](../Dockerfile), not its native Python runtime.
That is deliberate: applying an import first takes a full database snapshot
with `pg_dump`, and Render's native runtime has no PostgreSQL client, so every
import would be refused.

The image also pins **`postgresql-client-17`** from the PGDG repository.
Debian's default client is version 15, and `pg_dump` refuses to dump a server
newer than itself — against Render's PostgreSQL 16 it would fail every time.

On boot, [`deployment/render-entrypoint.sh`](render-entrypoint.sh) checks the
dangerous misconfigurations, runs `migrate` and `createcachetable`, then
starts gunicorn.

It begins as root only to take ownership of the mounted disk — Render mounts
it root-owned, and the app could not otherwise write flyers to it — then drops
to an unprivileged user with `gosu`. Nothing that serves a request runs as
root.

## 2. Create the stack

Render Dashboard → **New** → **Blueprint** → select this repository.

Render reads [`render.yaml`](../render.yaml) and creates:

- **`bharatnxt-toolkit`** — the web service (Docker, Singapore, `starter`)
- **`bharatnxt-db`** — PostgreSQL 16 (Singapore, `basic-256mb`, not exposed
  outside Render)
- **`bharatnxt-data`** — a 10 GB persistent disk mounted at `/var/data`

> Plan names and sizes in `render.yaml` reflect Render's tiers at the time of
> writing. If the dashboard rejects one, pick the nearest current equivalent —
> the only hard requirement is a plan that supports a **persistent disk**.

Render will prompt for the four `sync: false` values. Section 3 covers them.

## 3. The values you must supply

`BHARATNXT_SECRET_KEY` is generated by Render, and `DATABASE_URL` is wired from
the database automatically. You provide these:

### `BHARATNXT_OFFICE_NETWORKS` — the important one

The office's **public egress IP**, in CIDR form. Run this **from a machine on
the office network**:

```bash
curl https://ifconfig.me
```

If that prints `203.0.113.5`, set:

```
BHARATNXT_OFFICE_NETWORKS=203.0.113.5/32
```

> ⚠️ This is **not** the office LAN range. `192.168.x.x` and `10.x.x.x` are
> invisible to Render — putting them here blocks everyone, including you.
> Multiple offices or a backup line: comma-separate them.

### `BHARATNXT_DJANGO_ADMIN_PATH`

Django's built-in admin allows direct edits to any model, including users.
Move it off the default path:

```
BHARATNXT_DJANGO_ADMIN_PATH=internal-9f3a7c
```

Set it to an empty string to remove it entirely — the custom Admin Centre
covers normal administration.

### `BHARATNXT_ALLOWED_HOSTS` / `BHARATNXT_CSRF_TRUSTED_ORIGINS`

**Leave both blank** unless you attach a custom domain. The app reads
`RENDER_EXTERNAL_HOSTNAME` and adds the `.onrender.com` host to both
automatically.

With a custom domain, set:

```
BHARATNXT_ALLOWED_HOSTS=toolkit.bharatnxt.internal
BHARATNXT_CSRF_TRUSTED_ORIGINS=https://toolkit.bharatnxt.internal
```

CSRF origins **must** include the `https://` scheme.

## 4. First deploy

Trigger the deploy and watch the log. A healthy boot looks like:

```
==> BharatNXT Wave starting
==> Data root ready: /var/data
==> Applying migrations
==> Ensuring cache table
==> Starting gunicorn on 0.0.0.0:10000
```

If the entrypoint aborts, it says exactly what is wrong and exits non-zero, so
Render marks the deploy failed rather than serving a broken app:

| Message | Fix |
|---|---|
| `BHARATNXT_ENVIRONMENT must be 'production'` | Set it. Without it `DEBUG` stays on and the allow-list is off. |
| `BHARATNXT_DATA_ROOT is not set` | Set it to `/var/data`. |
| `BHARATNXT_DATA_ROOT=... does not exist` | The disk is not mounted, or `mountPath` and the variable disagree. |
| `pg_dump is missing from the image` | The Docker build did not complete the PGDG step. |

## 5. Create the first administrator

Render Dashboard → the service → **Shell**:

```bash
python manage.py createsuperuser
```

Then sign in and set that user's role to `SUPER_ADMIN` under
**Admin Centre → Employees**, so role-based screens behave correctly.

## 6. Verify the IP allow-list ⭐ do not skip

Everything else can be fixed later. This one decides whether the app is
actually protected.

Behind Render, the client address comes from `X-Forwarded-For`, and the app
counts `BHARATNXT_TRUSTED_PROXY_HOPS` in from the **right** of that header.
The default of `1` is correct for Render's single load balancer — but confirm
it rather than assuming.

**From inside the office**, open the app.

**If you reach the login page** — the hop count is right. Sign in, open
**Admin Centre → Activity Logs**, and confirm your `LOGIN` row shows the
office public IP. Done.

**If you get** `This BharatNXT Wave system is available only from the
authorised office network` — the app saw a different address. It recorded
which one. Open the Render **Shell**:

```bash
python manage.py shell -c "
from accounts.models import ActivityLog
for row in ActivityLog.objects.filter(action='PERMISSION_DENIED').order_by('-id')[:5]:
    print(row.created_at, row.metadata)
"
```

That prints the address the app actually resolved. Then:

- **Address is a valid public IP but not the one you expected** — your office
  egress IP differs from what `ifconfig.me` reported (multiple uplinks, or
  CGNAT). Add the address shown to `BHARATNXT_OFFICE_NETWORKS`.
- **Address looks internal (`10.x`, `100.64.x`)** — the hop count is wrong.
  Raise `BHARATNXT_TRUSTED_PROXY_HOPS` to `2` and retry.

> Never "fix" this by setting `BHARATNXT_OFFICE_NETWORKS=0.0.0.0/0`. That
> opens confidential data to the whole internet behind nothing but a login
> form. The shell query above answers the question without ever opening it.

## 7. Verify imports work ⭐ the other one not to skip

Applying an import runs `pg_dump` first. That path is the one thing that
cannot be proven anywhere except on the real database.

Upload a small test workbook and **apply** it. Then, in the Render Shell:

```bash
ls -la /var/data/audit/
```

A `.dump` file means `pg_dump` ran against Render's PostgreSQL and the whole
import pipeline is working.

If you instead see `pg_dump was not found on PATH`, the image built without
the PGDG step — check the build log.

## 8. Backups — Render's are not enough

Render backs up the **database**. It does not back up your disk. Both matter:

| What | Where | Covered by Render? |
|---|---|---|
| Scheme data, users, activity log | PostgreSQL | ✅ |
| **Scheme flyers** | `/var/data/private_uploads` | ❌ |
| Pre-import snapshots | `/var/data/audit` | ❌ |

Flyer *metadata* lives in the database while the *files* live on the disk, so
a database-only restore gives you rows pointing at files that no longer exist.

Pull the disk down periodically from the Render Shell, and **test a restore
before you rely on it** — an untested backup is not a backup.

Nothing prunes `/var/data/audit`. It grows by one full database dump per
applied import, on a 10 GB disk. Check it every few months.

Approximate, and worth confirming against Render's current pricing:

| Item | ~USD/month |
|---|---|
| Web service (`starter`) | ~$7 |
| PostgreSQL (`basic-256mb`) | ~$7 |
| 10 GB persistent disk | ~$2.50 |
| **Total** | **~$17 (roughly ₹1,400–1,500)** |

Render's free tier cannot run this: no persistent disk, and the instance
sleeps when idle.

## 10. Troubleshooting

| Symptom | Cause |
|---|---|
| `DisallowedHost` | Custom domain not in `BHARATNXT_ALLOWED_HOSTS`. The `.onrender.com` host is automatic; a custom one is not. |
| CSRF failure on login | `BHARATNXT_CSRF_TRUSTED_ORIGINS` missing the `https://` scheme. |
| 403 "authorised office network" | Section 6. |
| Flyers vanished after a deploy | `BHARATNXT_DATA_ROOT` is not pointing at the mounted disk. The files are gone; restore from your own backup. |
| Import refused, `pg_dump` error | Image built without PGDG, or a client/server version mismatch. |
| Lockout allows more than 5 attempts | `createcachetable` did not run — check the boot log. |
| Deploy fails on health check | Something is failing before gunicorn binds. Read the entrypoint output. |
| Blank 500 page | `/var/data/logs/bharatnxt.log`, or the Render log stream. |

## 11. How this differs from the self-hosted deployment

[`DEPLOYMENT.md`](DEPLOYMENT.md) covers the on-premise LAN install. Same
codebase, different switches:

| | Self-hosted | Render |
|---|---|---|
| Client IP from | `X-Real-IP`, trusted proxy list | `X-Forwarded-For`, hop count |
| `BHARATNXT_PROXY_MODE` | `xrealip` | `forwarded` |
| Allow-list contains | Office **LAN** subnet | Office **public** IP |
| Static files | nginx | WhiteNoise, in-process |
| Durable storage | The project directory | Mounted disk at `/var/data` |
| Database config | `BHARATNXT_DB_*` | `DATABASE_URL` |
| TLS | Your internal certificate | Render's edge |

Switching back to self-hosting later means changing configuration, not code.
